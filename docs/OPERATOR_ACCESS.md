# Event Commerce OS — Operator Access Runbook

This is the controlled-pilot human access procedure for Cloud/control-web. It is separate from POS device credentials, Event Edge machine credentials and payment-provider callback authentication.

## Security model

- Human access uses opaque bearer sessions prefixed `ecom_op_`.
- Session secrets are generated by Cloud tooling with 256 bits of randomness.
- Cloud stores only the SHA-256 digest.
- Sessions expire after 5–1440 minutes; default is 480 minutes.
- Operator identity, organisation membership and role are resolved from Cloud database state on every request.
- `x-organisation-id` is only a requested organisation scope. It never grants membership.
- Caller-supplied `x-actor-id` and `x-role` are ignored/stripped.
- Control-web retains the access token only in browser `sessionStorage` for the current tab/session.

This is suitable only for a bounded controlled pilot with tightly managed operators. It is not a claim of final enterprise IAM, SSO or MFA readiness.

## Roles

| Role | Intended authority |
| --- | --- |
| `PLATFORM_ADMIN` | Platform-wide setup, including organisation creation |
| `ADMIN` | Organisation configuration, operational actions, event close/reopen |
| `FINANCE` | Payment adjustments/history, financial close corrections and payment health |
| `SUPERVISOR` | Operational alert actions, supervised close corrections and manual-terminal confirmation where separately permitted |
| `VIEWER` | Read-only operational/financial visibility where explicitly allowed |

Manual terminal confirmation still requires the existing event-specific `PAYMENT_MANUAL_CONFIRM` permission in addition to an allowed operator role.

## 1. Create an operator identity

Run from an environment with Cloud database administrative access:

```bash
OPERATOR_AUTH_ACTOR='<named administrator/change ticket>' \
OPERATOR_DISPLAY_NAME='<operator name>' \
pnpm --filter @event-commerce/cloud-api operator-auth -- create-identity
```

Record the returned `OPERATOR_ID` in the pilot access register.

For a platform administrator only, add:

```bash
OPERATOR_PLATFORM_ADMIN=true
```

Do not grant `PLATFORM_ADMIN` for normal event operations.

## 2. Grant organisation membership

After the organisation exists:

```bash
OPERATOR_AUTH_ACTOR='<named administrator/change ticket>' \
OPERATOR_ID='<operator uuid>' \
OPERATOR_ORGANISATION_ID='<organisation uuid>' \
OPERATOR_ROLE='ADMIN|FINANCE|SUPERVISOR|VIEWER' \
pnpm --filter @event-commerce/cloud-api operator-auth -- grant-membership
```

Use the least-privileged role that satisfies the operator's event responsibility.

## 3. Create a short-lived session

```bash
OPERATOR_AUTH_ACTOR='<named administrator/change ticket>' \
OPERATOR_ID='<operator uuid>' \
OPERATOR_SESSION_TTL_MINUTES='480' \
pnpm --filter @event-commerce/cloud-api operator-auth -- create-session
```

The command outputs a one-time `OPERATOR_ACCESS_TOKEN`. Transfer it to the named operator through the approved secret channel. Do not paste it into tickets, chat history, source control or event documents.

A new session may be created at any time; there is no need to reuse an old token.

## 4. Use control-web

1. Open the approved control-web origin over HTTPS for non-local deployments.
2. Paste the `ecom_op_...` token into **Operator session** at the top of the application.
3. Select/use the intended organisation in the relevant screen.
4. Confirm the screen returns only the expected organisation/event data before performing any mutation.
5. Use **Clear** when handing over the workstation or ending the shift.

The token is kept in `sessionStorage`, so closing the browser tab/session removes the browser copy. Cloud expiry/revocation remains authoritative even if a browser copy survives unexpectedly.

## 5. Revoke a session

For an individual lost, copied or no-longer-needed token:

```bash
OPERATOR_AUTH_ACTOR='<named administrator/change ticket>' \
OPERATOR_SESSION_ID='<session uuid>' \
pnpm --filter @event-commerce/cloud-api operator-auth -- revoke-session
```

Revocation applies on the next Cloud request.

## 6. Revoke membership

When an operator should retain identity but lose access to one organisation:

```bash
OPERATOR_AUTH_ACTOR='<named administrator/change ticket>' \
OPERATOR_ID='<operator uuid>' \
OPERATOR_ORGANISATION_ID='<organisation uuid>' \
pnpm --filter @event-commerce/cloud-api operator-auth -- revoke-membership
```

## 7. Revoke the operator identity

For departure, compromise or broad access withdrawal:

```bash
OPERATOR_AUTH_ACTOR='<named administrator/change ticket>' \
OPERATOR_ID='<operator uuid>' \
pnpm --filter @event-commerce/cloud-api operator-auth -- revoke-identity
```

Identity revocation also revokes its active organisation memberships and sessions without deleting audit history.

## Pilot evidence to retain

- named operator and role;
- organisation(s) granted;
- access grant/revocation ticket or named approving administrator;
- session IDs issued (never plaintext tokens);
- shift/start/end or expiry window;
- any privilege change during the event;
- manual-terminal event permission grants;
- emergency revocation incidents and resolution.

## Current limitation

There is intentionally no password login, external identity provider, MFA or self-service token issuance in this slice. Before graduating beyond a tightly controlled pilot, integrate an approved enterprise identity provider and MFA/step-up policy while preserving the same server-side business-role checks.

Public HTTP also does not accept a caller-supplied second refund approver. Any workflow requiring two-person approval remains unavailable until the approving operator proves a separate authenticated session/step-up action.
